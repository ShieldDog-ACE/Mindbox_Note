## 1. 测试目标

验证一个**独立、自带三层记忆文件夹**的 MCP Server 是否满足:

1. 能被标准 MCP 客户端正常握手、发现工具、调用工具;
2. 三层记忆(短期 / 长期 / 永久)读写与检索正确;
3. 三个记忆根文件夹"不可删除"的保护有效;
4. 异常输入不打断连接;
5. 在真实客户端(Trae)中可用。

---

## 2. 测试环境

| 项 | 值 |
|---|---|
| 操作系统 | Ubuntu 24.04.4 LTS x64 |

| 传输协议 | stdio + JSON-RPC 2.0(换行分隔) |
| protocolVersion | `2025-06-18` |
| 真实客户端 | Trae CN(MCP 服务器 ID:`mcp_mindbox-memory`) |
| 客户端配置 | `~/.config/Trae CN/User/mcp.json` |

因为宿主盘是 **exfat**,`chmod` / `chattr +i` 均无效(挂载参数 `fmask=0022,dmask=0022`),
这也决定了"不可删除"只能做成**程序级保护**——这一点是本报告第 6 节风险项的来源。

**关键断言明细**

- `add_triple` 置信度 95 → `stored: 永久记忆`;65 → `stored: 长期记忆(待验证三元组)`;

## 6. 问题与风险

| # | 级别 | 问题 | 影响 | 建议 |
|---|---|---|---|---|
| 1 | 中 | **exfat 不支持权限锁**,`chmod`/`chattr +i` 无效,"不可删"仅为程序级 | 手动删除可绕过;下次启动自动重建但**内容会丢** | 定期备份整个 `Mindbox-MCP` 目录 |
| 2 | 中 | **并发写入无文件锁**:多 agent 同时写同一 JSON 存在覆盖风险 | 极端场景下丢一条记忆 | 后续引入 `flock` 或原子写(写临时文件 + `os.replace`) |
| 3 | 中 | **中文分词为无依赖实现**(单字 + 双字,非 jieba) | 召回不如 jieba 精准,低分项有噪声 | 若需高精度可选择性接入 jieba(代价:引入依赖) |
| 4 | 低 | 晋升门槛 `引用 > 100` 偏高 | 实际使用中条目几乎升不到永久 | 按使用强度调低阈值或加时间衰减维度 |
| 5 | 低 | 无鉴权 / 无路径黑名单 | 本机 stdio 进程,风险较低 | 如需远程接入 HTTP 形态时再补 Token |
| 6 | 低 | 仅 Trae 实测接入 | Cursor / Claude Code / CodeBuddy 未做真机验证 | 已提供 `mcp.json`,按文档粘贴即可 |
| 7 | 提示 | 客户端需**重载窗口**才加载新 MCP | 首次接入看不到工具 | 已写入文档 FAQ |

## 7. 结论

1. **可用性**:三层记忆的写入、检索、升降级、图扩展、会话快照全链路打通,
   协议握手与工具发现符合 MCP 规范,**46/46 断言 + 22 次真机调用全部通过**。
2. **安全性**:三个记忆根文件夹的删除保护在工具层与存储层双重生效,越界路径被拒绝。
3. **健壮性**:未知工具、未知方法、协议错误均不会打断连接;stdout 纯净,日志不污染协议流。
4. **零依赖**:纯标准库实现,任意装 Python 3 的机器可直接运行,无需 pip。
5. **待改进**:并发写入加锁、分词精度、晋升阈值调优——均为增强项,**不阻塞当前使用**。

> **总体判定:功能达标,建议投入使用。**
> 已知风险集中在"exfat 权限锁缺失"与"并发写入",前者用备份规避,后者在单 agent 使用下无实际影响。
